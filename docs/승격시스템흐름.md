# 월계는 처음이라 — 승격 시스템 흐름

---

## 1. 왜 승격이 필요한가

승격을 빼면 이 앱은 **월계1동 Q&A 게시판**이 되고, 그건 에브리타임이 이미 한다.

이 제품의 문제 정의는 **"모른다는 걸 모른다"** 이다. 그런데 질문 목록은 찾아봐야 나온다. 뭘 물어야 할지 모르는 사람은 Q&A 아카이브도 찾지 못한다. 검색창은 질문을 아는 사람에게만 작동한다.

**승격은 "찾아야 아는 것"을 "안 찾아도 오는 것"으로 바꾸는 장치다.**

| | 3월에 누가 물어봄 | 9월에 온 사람 |
|---|---|---|
| **승격 없음** | 답 달림 → 게시판에 남음 | 그런 게 있는 줄 모름 → 똑같이 당함 |
| **승격 있음** | 답 달림 → 할 일로 승격 | 상황 입력하자마자 목록에 떠 있음 |

부수 효과로 콜드스타트도 여기서 풀린다. 시드 30~60개로 시작해도 쓰는 만큼 목록이 자란다. 승격이 없으면 할 일 목록은 팀이 넣은 시드에서 영원히 늘지 않고, "쓸수록 쌓인다"는 주장이 거짓이 된다.

## 2. 전체 흐름

```
[질문]
  │
  ▼
AI 답변 시도
  │
  ├─ GROUNDED ──────────────► 끝 (이미 지식에 있음. 승격 불필요)
  │
  └─ PARTIAL / UNKNOWN
       │
       ▼
   ① 답변 대기 ──► ② 주민이 답변 ──► ③ 다른 주민이 확인
       (OPEN)          (ANSWERED)         (정렬용)
                                            │
                                            ▼
                                      ④ 운영자 검토 큐
                                            │
                                ┌───────────┴───────────┐
                              기각                     승격
                                │                       │
                                ▼                       ▼
                        답변은 남음              ⑤ AI 초안 생성
                        (검색은 됨)                     │
                                                        ▼
                                                ⑥ 운영자 편집·확정
                                                   숫자·기한·조건 검증
                                                        │
                                                        ▼
                                                  ⑦ 할 일 발행
                                                   (PROMOTED)
                                                        │
                                                        ▼
                                        ⑧ 다음 사람 목록에 자동 노출
                                                        │
                                                        ▼
                                          ⑨ 6개월 후 신선도 재검토
                                                        │
                                                        └──► ④로 복귀
```

---

## 3. 단계별 상세

| 단계 | 누가 | 하는 일 | 데이터 변화 |
|---|---|---|---|
| **0** | AI | 로컬 지식으로 답변 시도 | `Question.confidence` 기록 |
| **①** | — | `PARTIAL`/`UNKNOWN`만 답변 대기 목록에 노출 | `status = OPEN` |
| **②** | 주민 (로그인) | 살아본 경험으로 답변 작성 | `Answer` 생성, `status = ANSWERED` |
| **③** | 다른 주민 | "맞아요" 확인 | `Confirmation` 생성 |
| **④** | 운영자 | 큐에서 검토 — 확인 수 순 정렬 | — |
| **⑤** | AI | 할 일 초안 생성. 문장 칸도 답변의 완전한 원문 문장만 허용한다. 실패하면 운영자가 빈 양식에서 직접 작성 | (임시 데이터) |
| **⑥** | 운영자 | **숫자·기한·조건 검증 후 확정** | — |
| **⑦** | 시스템 | 할 일 발행 | `Task` 생성, `status = PROMOTED` |
| **⑧** | — | 조건 맞는 다음 사용자에게 노출 | `matching` 통과 |
| **⑨** | 사용자 | "바뀌었어요" 누적 시 재검토 | `④`로 복귀 |

## 4. 상태 값

```
Question.status   OPEN → ANSWERED → PROMOTED
                                  ↘ (기각 시 ANSWERED 유지)

Task.source       SEED | PROMOTED
Task.verifiedAt   마지막 확인일 — 6개월 경과 시 "오래된 정보" 배지

AI confidence     GROUNDED | PARTIAL | UNKNOWN
```

## 5. 중요한 분기 셋

### 5.1 `GROUNDED`는 승격 경로에 들어가지 않는다

이미 할 일이나 확인된 답변에 있는 내용이라 또 만들 필요가 없다. **AI가 답하지 못한 질문만** 이 파이프라인을 탄다. 승격 대상이 자동으로 걸러진다.

### 5.2 기각돼도 정보는 사라지지 않는다

운영자가 기각하면 `Question`은 `ANSWERED`로 남고 답변도 그대로 검색된다. 단지 할 일 목록에 자동으로 뜨지 않을 뿐이다.

**기각의 의미는 "틀렸다"가 아니라 "모두에게 밀어줄 만큼은 아니다"이다.**

### 5.3 ⑥이 오정보 방어의 마지막 관문이다

AI 초안은 주민 답변의 완전한 원문 문장만 채우지만, 그 답변 자체가 맞는지는 사람이 확인해야 한다. 여기를 통과한 값만 할 일 카드에 원문으로 박힌다. 오정보 방어 3층("숫자는 AI가 다시 쓰지 않는다")이 실제로 성립하는 지점이 여기다.

## 6. 조건 추론 (⑤에서 AI가 하는 일)

```
입력   질문 텍스트
       확인된 답변
       질문한 사람들의 상황 스냅샷 (거주형태·계약형태)

출력   title / why / howTo             ← 답변의 완전한 원문 문장만
       dueOffsetDays / category
       housingTypes[] / contractTypes[]    ← 제안일 뿐
```

물어본 사람 5명이 전부 원룸이었다면 `housingTypes=[ONE_ROOM]`을 제안한다. **운영자가 확정하기 전까지는 제안이다.**

---

## 7. 확인 임계값을 두지 않는 이유

초기에는 사용자가 적어 확인이 3개씩 모이지 않는다. 임계값을 두면 오히려 병목이 되어 **승격이 한 번도 일어나지 않는 상태로 본선에 갈 수 있고**, 그러면 핵심 기능을 시연하지 못한다.

따라서 **운영자가 답변 큐 전체를 보고, 확인 수는 정렬 기준으로만 쓴다.** 확인이 많은 답변이 위로 올라오고 운영자가 판단한다. 상태 하나가 줄고 `lib/promotion.ts`도 단순해진다.

규모가 커지면 그때 임계값을 넣는다.

---

## 8. 데모 설계

승격 전체 사이클을 심사위원 앞에서 돌리려면 시간이 걸리므로 **마지막 한 단계만 남겨둔다.**

1. 승인 대기 큐에 답변 하나를 올려둔 상태로 시작
2. 심사위원 앞에서 **승인 버튼 클릭**
3. 관람자 화면 새로고침
4. **할 일 목록에 새 항목이 나타남**

30초면 되고, "질문이 지식이 된다"는 논지가 화면으로 증명된다.

---

## 9. 이번 범위에서 빼는 것

**기존 할 일과의 중복 병합.** 승격하려는 내용이 이미 있는 할 일과 겹칠 때 자동으로 합치는 기능은 만들지 않는다. 운영자가 큐에서 눈으로 거르면 되는 규모고, 자동 병합은 잘못 합쳤을 때 되돌리기가 까다롭다. 항목이 수백 개로 늘면 그때 넣는다.
