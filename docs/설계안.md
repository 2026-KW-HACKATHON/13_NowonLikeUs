# 월계는 처음이라 — 설계안

**한 줄 정의:** 월계1동에 처음 온 사람이 자기 상황에 맞는 할 일 목록을 받고, 막히면 묻고, 그 질문과 답이 다음 사람의 목록으로 쌓이는 앱.

---

## 1. 제품 정의와 핵심 순환

### 1.1 핵심 순환

```
   ┌─────────────────────────────────────────────┐
   │                                             │
   ▼                                             │
[상황 입력]                                       │
구역·거주형태·계약형태·이사일                        │
   │                                             │
   ▼                                             │
[내 할 일 목록]  ◄──────────────── [승격]          │
나에게만 해당하는 것만              확인된 답이       │
   │                              정식 항목이 됨    │
   ▼                                   ▲          │
[막히면 질문] ──► [AI 답변] ──► [주민이 확인해줌] ───┘
                로컬 지식 참조
```

이 고리 하나가 제품의 전부다. 여기서 두 가지가 동시에 나온다 — **쓸수록 월계1동 로컬 지식이 쌓이고, 콜드스타트가 저절로 풀린다.**

### 1.2 가장 가까운 선행 서비스와의 차이

발표에서 반드시 나올 질문 셋에 대한 답이 설계에 박혀 있어야 한다. 상세 비교는 [기획서 4절](기획서.md) 참조.

| | 정부 서비스<br>(구삐·정부24) | **이사노트** | 이 앱 |
|---|---|---|---|
| 진입 조건 | **알고 찾아와야** 함 | 이사일·유형 입력 | 구역과 상황만 넣으면 됨 |
| 다루는 범위 | 행정 | **행정 절차만** | **행정 + 동네 생활** (쓰레기 요일·봉투·개통·병원) |
| 지역 단위 | 전국 동일 | **전국 공통** | **월계1동 단위** |
| 개인화 | 없음 | **시점(D-30~D+3)** | **상황별로 갈림** |
| 정보 갱신 | 기관이 고침 | 고정 | **살아본 사람이 고침** |

**"이거 이사노트 아닌가요?"** — 타임라인 구조는 같다. 갈리는 건 셋이다. ① 동네마다 다른 생활 정보를 다룬다 ② 개인화 축이 *시점*이 아니라 *상황*이다 ③ 질문이 승격돼 목록이 자란다. **타임라인 자체를 차별점으로 내세우면 안 된다.**

**"곧 정부가 하지 않나요?"** — 국민권익위가 **2026-09-16** 「전입자 생활정보 사전안내 강화 방안」을 행안부·기초지방정부에 권고했고 여기엔 생활폐기물 배출 정보까지 포함된다. 다만 권고 내용은 **"누리집·전자책 등으로 종합 안내"**, 즉 정적 안내물이라 상황별 분기도 갱신 구조도 없다. 강제도 아니어서 지자체가 각자 이행한다. **노원구가 이행하려면 도구가 필요하고 이 설계가 그 도구다.**

### 1.3 개인화 축은 "시점"이 아니라 "상황"이다

이사일 기준 D+N 체크리스트는 누구에게나 같아서 그냥 블로그 글이다. 실제로는 상황에 따라 할 일이 갈린다.

| 상황 | 갈리는 할 일 |
|---|---|
| 전세 | 확정일자 최우선 — 안 받으면 보증금을 잃을 수 있음 |
| 월세 | 전입신고 + 월세 세액공제 |
| 기숙사 | 전입신고 처리 방식이 다름 |
| 원룸·빌라 | 종량제 봉투 직접 구매, 분리수거 요일 준수 |
| 아파트 | 관리사무소가 대행하는 항목이 많음 |
| 차량 보유 | 거주자 우선주차 신청 |
| 반려동물 | 동물등록 (미등록 시 과태료) |

**해당 없는 항목은 아예 보이지 않는다.** 이것이 일반 체크리스트 앱과 갈리는 지점이다.

### 1.4 할 일 하나의 구성

- **뭘 해야 하나** — 전입신고
- **안 하면 어떻게 되나** — 기한을 넘기면 과태료, 보증금 보호를 못 받음
- **언제까지** — 이사일 기준 D+N
- **어디서 어떻게** — 월계1동 주민센터 실주소·전화(바로 전화 걸기) 또는 정부24 링크

세 번째가 핵심이다. **"안 하면 어떻게 되는지"가 없으면 사람은 안 한다.** 대부분의 체크리스트가 이걸 빼먹는다.

### 1.5 원칙 — AI는 정보를 생성하지 않는다

행정·생활 정보는 **팀이 조사해 넣은 시드 데이터와 주민이 확인한 답변만** 사용한다. 전입신고 기한을 AI가 잘못 말하면 사용자가 **실제로 과태료를 낸다.**

AI의 역할은 셋뿐이다 — 질문에 맞는 할 일 카드 고르기(문장은 쓰지 않음), 질문 중복 판정, 승격 초안 작성. **정보의 출처는 항상 사람이다.**

## 2. 데이터 모델과 화면

### 2.1 로그인 경계

| 하는 일 | 로그인 |
|---|---|
| 상황 입력, 할 일 목록 보기, 완료 체크 | **불필요** — 브라우저(localStorage)에 저장 |
| 질문하기 | **불필요** — 질문은 익명. 로그인 상태면 `askerId` 만 저장하고 닉네임은 공개 목록에 내보내지 않는다 |
| 답변 달기, "맞아요" 누르기 | **필요** |
| 승격 (할 일 발행) | **ADMIN** — 역할은 DB 재조회 |

받으러 오는 사람에겐 문턱이 없고, 남들이 믿고 쓰게 되는 걸 남기는 사람만 계정을 만든다. 처음 온 사람이 회원가입부터 해야 하면 그 자체가 앱을 안 쓰는 이유가 된다. 질문은 막힌 사람이 하는 행동이라 받는 쪽에 둔다.

### 2.2 수집하는 정보 — 상세 주소를 받지 않는다

**확정 사항:** 상세 주소(번지·건물명·호수)는 **수집하지 않는다.**

쓰레기 배출 요일이 갈리는 **구역 단위**만 고르게 하면 기능상 충분하고, 그 이상은 쓰이지도 않으면서 개인정보 부담만 늘린다. 처음 온 사람에게 상세 주소를 입력시키는 것 자체가 이탈 요인이기도 하다.

수집 항목은 다음이 전부다.

```
구역          월계1동 내 구역 (쓰레기 배출 요일이 갈리는 단위)
거주형태      원룸 | 오피스텔 | 기숙사 | 아파트 | 빌라
계약형태      월세 | 전세 | 기숙사비 | 자가
이사일        날짜
차량 보유     예/아니오
반려동물      예/아니오
학생 여부     예/아니오
```

> **선행 조사 필요:** 월계1동 안에서 쓰레기 배출 요일이 실제로 구역별로 갈리는지 확인해야 한다. 동 전체가 동일하다면 구역 선택 자체가 불필요하고 입력이 한 단계 더 줄어든다.

### 2.3 데이터 모델

**`Task` — 할 일 (시드 + 승격)**

```prisma
model Task {
  id             String   @id @default(cuid())
  title          String              // "전입신고 하기"
  why            String              // "기한을 넘기면 과태료, 보증금 보호를 못 받습니다"
  dueOffsetDays  Int?                // 이사일 기준. null이면 기한 없음
  howTo          String              // 절차 설명
  linkUrl        String?             // 정부24 등
  placeName      String?             // "월계1동 주민센터"
  placeAddress   String?
  placePhone     String?             // 바로 전화 걸기
  category       TaskCategory        // ADMIN | WASTE | HOUSING | LIFE

  // 노출 조건 — 빈 배열/false는 "조건 없음"
  housingTypes   HousingType[]
  contractTypes  ContractType[]
  requiresCar    Boolean  @default(false)
  requiresPet    Boolean  @default(false)
  studentOnly    Boolean  @default(false)

  source         TaskSource          // SEED | PROMOTED
  promotedFromQuestionId String?
  sourceNote     String?             // 출처와 확인 경로
  verifiedAt     DateTime            // 마지막 확인일
  isPublished    Boolean  @default(true)
}
```

노출 조건을 별도 테이블로 빼지 않고 `Task`에 직접 단다. 조건이 단순하고 개수가 적어 별도 테이블은 과설계다. 조건 조합이 복잡해지면 그때 분리한다.

**`Question` / `Answer` / `Confirmation`**

```prisma
model Question {
  id              String   @id @default(cuid())
  text            String
  askerId         String
  ctxHousingType  HousingType?    // 물어본 사람의 상황 스냅샷
  ctxContractType ContractType?
  aiAnswer        String?
  confidence      Confidence      // GROUNDED | PARTIAL | UNKNOWN
  status          QuestionStatus  // OPEN | ANSWERED | PROMOTED
  createdAt       DateTime @default(now())
}

model Answer {
  id         String @id @default(cuid())
  questionId String
  authorId   String
  text       String
  verifiedAt DateTime @default(now())
}

model Confirmation {
  id       String @id @default(cuid())
  answerId String
  userId   String
  @@unique([answerId, userId])
}
```

상황 스냅샷을 남기는 이유는, 승격 시 **"이 답이 누구에게 해당하는지"** 를 추론하는 근거가 되기 때문이다. 전세 세입자가 물어서 나온 답이 기숙사생에게 뜨면 안 된다.

**`User`** — `id · email · passwordHash · nickname · role(MEMBER | ADMIN)`

### 2.5 API

```
POST /api/tasks/match              프로필 → 해당 할 일 목록
```

프로필은 클라이언트(localStorage)에 있으므로 `/api/tasks/match`에 POST로 실어 보내 서버에서 필터링한다.

### 2.6 순수 로직 분리와 테스트

프로젝트 규칙상 **상태가 걸린 순수 로직만** 단위 테스트한다(Vitest).

| 파일 | 하는 일 | 테스트 이유 |
|---|---|---|
| `lib/matching.ts` | 프로필 → 할 일 필터링 | 조건이 하나라도 어긋나면 안 보여야 하고, 빈 배열은 "전원 해당"으로 처리해야 함 |
| `lib/dday.ts` | 이사일 + `dueOffsetDays` → 남은 날짜, `verifiedAt` → 신선도 | 기한 지난 항목 판정이 여기 걸림 |
| `lib/promotion.ts` | 승격 큐 진입·정렬 | 상태 전이 |
| `lib/grounding.ts` | AI가 준 `sourceIds`를 실제 id와 대조해 `confidence` 강등 | **오정보 방어 2층 그 자체** |

UI·라우트 배선은 수동 확인으로 검증한다.

## 3. AI 파이프라인과 오정보 방지

### 3.1 질문 답변 — 임베딩을 쓰지 않는다

시드 할 일 30~60개 + 확인된 답변 수십 개 = **100건 내외, 1~2만 토큰**이라 Gemini 컨텍스트에 통째로 들어간다. 벡터 DB도 임베딩도 만들지 않고 전체를 프롬프트에 주입한다. 수백 건을 넘으면 그때 키워드 1차 필터를 넣는다.

**프롬프트 골격**

```
[규칙]
아래 <지식>에서 질문에 답하는 데 필요한 항목만 고른다.
없으면 confidence 는 UNKNOWN, sourceIds 는 빈 배열. 추측하지 않는다.
근거로 쓴 항목의 id를 그대로 넣는다. 없는 id를 만들지 않는다.

[지식]
task:12   | 전입신고 | 기한 이사일+N일 | 월계1동 주민센터 | ...
answer:47 | 확인 5회 | Q 종량제 봉투 어디서 사나요 | A ...

[사용자 상황]  원룸 · 월세 · 이사일 2026-03-02
[질문]        음식물 쓰레기는 어떻게 버려요?
```

**출력은 구조화해서 받는다**

```json
{ "sourceIds": ["task:12"], "confidence": "GROUNDED" }
```

**AI는 문장을 쓰지 않는다.** 처음에는 AI가 안내 문장을 쓰고 숫자가 든 문장을 정규식으로 막았는데, "열나흘" 같은 한글 수치는 놓치고 "이번" · "이사일"은 숫자로 잘못 잡았다. 그래서 AI 문장을 화면 · DB 어디에도 쓰지 않고, 근거가 확인되면 서버 고정 문구("관련 항목의 원문 카드를 확인해 주세요.")만 붙인다(#31). 후보는 사용자 상황으로 먼저 거른 할 일 전체다(#32).

| 값 | 의미 | 화면 |
|---|---|---|
| `GROUNDED` | 로컬 지식만으로 답함 | **초록** — "월계1동에서 확인된 정보" + 출처 링크 |
| `PARTIAL` | 일부만 로컬 근거 | **노랑** — "일부만 확인됨" |
| `UNKNOWN` | 지식에 없음 | **회색** — "아직 아무도 확인하지 않았습니다" + 답변 요청 |

**`UNKNOWN`이 순환의 시작점이다.** 모른다고 답하고 끝나는 게 아니라 그 자리에서 커뮤니티로 넘어간다. **AI가 모르는 것이 곧 이 앱이 자라는 지점이다.**

### 3.2 오정보 방지 — 6층 방어

행정 정보가 틀리면 사용자가 실제로 과태료를 낸다. 한 겹으로는 부족하다.

| 층 | 내용 |
|---|---|
| **1 · 생성 금지** | AI는 행정·생활 사실을 만들지 않는다. 지식에 없으면 `UNKNOWN` |
| **2 · 근거 id 서버 검증** | AI는 존재하지 않는 id를 지어낸다. 서버가 실제 id 집합과 대조해 허구가 섞이면 `confidence` 강등, 전부 허구면 `UNKNOWN`으로 강등 |
| **3 · 숫자는 AI가 다시 쓰지 않는다** | AI는 문장을 쓰지 않고 카드만 고른다. 안내 문장은 서버 고정 문구. **금액·기한·장소는 할 일 카드를 DB 원문 그대로 붙인다.** 숫자가 AI를 통과하지 않으면 숫자는 틀리지 않는다 |
| **4 · 사람 승인** | 승격은 운영자 승인 없이 일어나지 않는다 |
| **5 · 신선도** | `verifiedAt` 6개월 경과 시 "오래된 정보" 배지. 사용자가 "지금도 맞아요 / 바뀌었어요"를 누를 수 있고, 후자가 쌓이면 운영자 큐로 |
| **6 · 신고** | 잘못된 답변 신고 → 즉시 노출 보류 → 운영자 검토 |

3층의 화면 형태는 다음과 같다.

```
[안내]     관련 항목의 원문 카드를 확인해 주세요.      ← 서버 고정 문구, AI 미개입
[카드]     ┌─────────────────────────────┐
           │ 전입신고 하기                 │
           │ 기한: 이사일로부터 N일         │  ← DB 원문, AI 미개입
           │ 안 하면: (원문 그대로)         │
           │ 월계1동 주민센터 · 전화 걸기    │
           └─────────────────────────────┘
```

여기에 더해 카드에 **"○년 ○월 기준"** 표기와 **"최종 확인은 주민센터 문의"** 고지를 단다.

### 3.3 질문 중복 판정

새 질문이 들어오면 기존 질문 제목 목록을 주고 **"같은 질문이 있으면 그 id, 없으면 null"** 만 받는다. 같으면 기존 질문으로 합쳐 **답변이 흩어지지 않게** 한다. 에브리타임에서 같은 질문이 매년 반복되는 문제를 푸는 지점이고, 부수적으로 API 호출도 준다.

오판정 대비로 **"다른 질문이에요"** 버튼을 두어 사용자가 분리할 수 있게 한다.

### 3.4 승격 초안 생성

```
입력   질문 + 확인된 답변 + 질문한 사람들의 상황 스냅샷
출력   title / why / dueOffsetDays / howTo / category
       housingTypes[] / contractTypes[]   ← 제안일 뿐
```

물어본 5명이 전부 원룸이면 `housingTypes=[ONE_ROOM]`을 제안한다. **운영자가 확정하기 전까지는 제안이다.**

### 3.5 AI가 죽어도 앱은 산다

Gemini 호출 실패나 쿼터 초과 시 앱이 멈추면 안 된다. 본선 시연 중에 일어날 수 있는 일이다.

- 답변 생성 실패 → 키워드 검색 결과만 카드로 보여주고 *"지금은 자동 답변을 드릴 수 없습니다. 관련 항목입니다"*
- 중복 판정 실패 → 새 질문으로 등록 (나중에 병합 가능)
- 승격 초안 실패 → 운영자가 빈 양식에서 직접 작성

**AI는 증강이지 필수 경로가 아니다.** 할 일 목록·상황 매칭·질문 등록·답변·확인은 전부 AI 없이 동작한다.

## 4. 승격 흐름

상세는 [승격 흐름 문서](승격시스템흐름.md) 참조. 요약하면:

```
질문 → AI 답변
     ├─ GROUNDED → 끝 (이미 지식에 있음)
     └─ PARTIAL/UNKNOWN
          → 주민 답변 → 확인(정렬용) → 운영자 검토 큐
          → AI 초안 → 운영자 편집·확정 → 할 일 발행
          → 다음 사람 목록에 노출 → 6개월 후 재검토
```

**확인 임계값은 두지 않는다.** 초기에는 확인이 모이지 않아 승격이 한 번도 일어나지 않을 수 있고, 그러면 핵심 기능을 시연하지 못한다. 운영자가 큐 전체를 보고 확인 수는 정렬 기준으로만 쓴다.

## 7. 리스크

### 7.1 시드 데이터가 최대 병목 — 코드가 아니라 조사다

할 일 20~30개를 **정확하게** 채워야 한다. 쓰레기 배출 요일, 종량제 봉투 판매처, 대형폐기물 신고 절차, 전입신고 기한과 과태료, 주민센터 전화번호. 전부 노원구청 홈페이지와 주민센터 전화로 확인해야 하는 값이다.

이게 안 되면 **앱은 빈 껍데기이고 데모가 성립하지 않는다.** 코드는 다 돌아가는데 보여줄 게 없는 상태가 된다.

**대응**
- 4일 중 **1일을 조사에 통째로 배정**하고 인력을 몰아넣는다
- **틀린 값은 넣지 않고 비워둔다.** 확인 안 된 항목은 아예 만들지 않는다 — 제품의 전제가 "정보 출처는 항상 사람"인데 시드부터 어기면 안 된다
- **출처와 확인 날짜를 `sourceNote` · `verifiedAt`에 남긴다.** 조사 기록 자체가 지역적합성 점수의 근거가 된다

### 9.4 Git 규칙 (정우성 관리)

심사 항목에 "코드 및 GitHub 관리 상태"가 포함되므로 히스토리를 관리 대상으로 본다.

#### 브랜치 구조

```
useong/화면작업   ─┐
huitae/api작업    ─┼─→ dev (PR로 자주 머지) ─→ (주기적으로) ─→ master ─→ Vercel 자동 배포
kwonseop/프롬프트 ─┤
yongmin/시드데이터 ─┘
```

- **작업 브랜치 → `dev`** — 평소 작업은 전부 여기로 PR. 자주, 작은 단위로 머지한다
- **`dev` → `master`** — `dev`가 안정된 상태일 때만 주기적으로 머지한다 (회의 전, 시연 준비 직전). 머지되는 순간 실제 배포에 반영되므로 신중하게 진행한다
- `dev → master` 머지는 **정우성(저장소 관리)** 이 진행한다
- **`master`·`dev` 모두 직접 push를 막는다.** 반드시 작업 브랜치 + PR로 작업한다

#### 작업 순서

```bash
# 1. dev 최신화 (작업 시작 전 항상 먼저)
git checkout dev
git pull origin dev

# 2. 본인 이름으로 브랜치 생성
git checkout -b <이름>/<작업내용>      # 예: useong/task-list

# 3. 작업 & 커밋 (여러 번 나눠도 됨 — squash로 정리된다)
git add <바꾼 파일>
git commit -m "Feat: 커밋 메시지"

# 4. 원격에 push (처음만 -u)
git push -u origin <이름>/<작업내용>
```

그다음 **Compare & pull request** 로 PR을 생성하되 **base가 `master`가 아니라 `dev`인지 확인**한다. 팀원 1명 승인 후 **Squash and merge** 로 병합하고, 병합 후 **Delete branch** 로 정리한다. 다음 작업은 다시 1번부터 반복한다.

#### 커밋 메시지 규칙

형식: `<타입>: <제목>`

| 타입 | 의미 |
|---|---|
| `Feat` | 새 기능 추가 |
| `Fix` | 버그 수정 |
| `Docs` | 문서 수정 |
| `Style` | 포맷팅 등 로직에 영향 없는 변경 |
| `Refactor` | 기능 변경 없는 코드 구조 개선 |
| `Test` | 테스트 코드 추가/수정 |
| `Chore` | 빌드, 패키지 매니저, 설정 등 |

- 제목은 50자 이내, 끝에 마침표를 붙이지 않는다
- 제목은 명령문·현재형으로 쓴다 ("추가함" ✗ → "추가" ✓)
- 본문이 필요하면 제목 뒤 한 줄을 띄우고, **"무엇을 했는지"보다 "왜 했는지"** 를 쓴다

```
Feat: 프로필 매칭에 반려동물 조건 추가

동물등록 미이행 과태료 항목을 넣으면서 반려동물 보유 여부로
분기할 필요가 생김.
```

#### 주의사항

- **커밋 메시지·PR 본문에 AI 작성자 표기(`Co-Authored-By` 등)를 넣지 않는다.** 심사에 GitHub 관리 상태가 포함되므로 컨트리뷰터 목록을 팀원 명의로만 유지한다
- **Prisma 스키마나 API 요청·응답 형태를 바꾸는 PR은 병합 전에 관련 담당자에게 알린다.** 정우성(화면)·우희태(API)·김권섭(AI)이 같은 스키마 위에서 병렬로 작업하므로, 말 없이 바꾸면 세 명이 동시에 깨진다 (9.1절 참조)
- 시드 데이터는 `sourceNote`·`verifiedAt` 없이 커밋하지 않는다
- README에 프로젝트 소개, 실행 방법, 아키텍처, 역할 분담을 포함한다
